# N4 — Bounded scheduling, memory, cancellation, and shutdown

**Status:** necessary requirement; bounded per-call spawned admission is
implemented for one Runtime path, while full N4 acceptance remains open.

**Primary owner:** `PhysicalDesign/Runtime/`.

## Goal

Keep preparation, search, native computation, speculative work, cancellation,
and cleanup within explicit time, CPU, memory, and work bounds.

## Current frontier

`9f432cd`, repaired by `f5ffd47`, bounds one spawned symbolic unary fan-out per
call. It admits bounded in-flight and queued work and reports typed admission,
payload, result, deadline-before-start, and worker-failure exits. A failed
cancellation does not release capacity: the third submission waits until a real
task completion. This remains short of N4's unified Python/native admission,
global memory/cache bounds, cancellation checkpoints in native work, bounded
teardown, and exact parent-deadline propagation.

## Required behavior

- Use one absolute routing deadline across planning, search, materialization,
  cleanup, and result collection.
- Give every task an absolute deadline, work cap, memory allowance, result-size
  limit, cancellation contract, and maximum non-yield interval.
- Count Python processes and native threads under one admission policy.
- Bound queued payloads, speculative candidates, caches, proof state, and native
  contexts.
- Apply backpressure before memory or queue growth becomes unbounded.
- Require cancellation checkpoints inside Python and long native operations.
- Bound pool shutdown, worker cleanup, checkpoint writing, and native teardown.
- Distinguish deadline, work-cap exhaustion, cancellation, termination, worker
  failure, and infeasibility.

## Cancellation and termination

Cancellation is a request or reason. Termination is the completed lifecycle
transition in which the task stops executing and releases all live task
resources. A set cancellation token does not prove that the task has stopped.

Graceful and forced termination remain distinct. Terminating one task normally
does not terminate its persistent worker process. See [R6](../../R/R6/R6.md) for the
complete demotion, termination, and worker-lifecycle contract.

## Pressure-aware cleanup budgets

The upstream Python coordinator owns pressure assessment and grants an
immutable budget snapshot before Runtime admits work. The snapshot identifies
the absolute work deadline, the absolute cleanup cutoff, and whether forced
termination is authorized. Runtime applies that snapshot mechanically; it does
not infer idleness, extend a deadline, or choose a longer cleanup allowance.

The work deadline bounds useful planning and execution. The cleanup cutoff
bounds cancellation signalling, graceful exit, forced termination when
authorized, process reaping, and release acknowledgement. When cancellation is
observed before the work deadline, cleanup begins at that observation; it may
not use the unspent work budget as additional cleanup time.

Pressure classes may choose different cleanup cutoffs before admission. When
new critical work requires capacity while cleanup is in progress, an explicit
coordinator revocation may shorten the existing cleanup cutoff and skip or
shorten cooperative grace. It may never extend either cutoff. Runtime does not
count a permit as free until process exit and resource release are acknowledged.

The concrete pressure classes, numeric allowances, grace intervals, and
forced-termination escalation sequence are coordinator policy and require
measurement and versioned agreement. They are not implicit Runtime defaults.

## Salvage budget

N6 stale-result review and checkpoint construction consume bounded budgets.
They cannot delay critical worker release. A result arriving after a deadline
cannot change that run's reported outcome; completed immutable claims may be
considered for a future run only through a new N6 review.

## Acceptance

- No cleanup or pool shutdown extends the deadline without an explicit bounded
  allowance.
- Runtime receives explicit work and cleanup cutoffs; it never reconstructs or
  extends either budget from elapsed time or observed spare capacity.
- Critical work can reclaim resources within the declared preemption bound.
- Memory and task queues remain within configured limits.
- Forced termination releases resources and produces explicit partial evidence.
- No timeout, cancellation, demotion, or termination becomes an infeasibility
  proof.
